# Calendar: clock, speed and date

How a save keeps time: the game clock that times events, the calendar speed, the table that turns clock values into dates, and the copy of the date shown in the header. Clock values appear in the script states ([script-states.md](script-states.md#times)), the money journal ([finances.md](finances.md)) and the statistics lists ([statistics-lists.md](statistics-lists.md)). The speed and the day table sit in an engine component in the entity data, found by pattern.

Checked on 604: one game started in 1900 and played into 2061, saved at several speeds, and catalog saves [6417707](https://mod.io/g/transportfever3/m/333151), [6425796](https://mod.io/g/transportfever3/m/mynewsavenotfinished1) and [6428935](https://mod.io/g/transportfever3/m/emerald-shores3) compared with the game's windows. On 585, two saves gave dates in the right year but were not checked to the day. The calendar speed field, the day table and the header date were also read on the 120 catalog saves of [versions.md](versions.md), 568 to 604.

## The game clock

Times in a save count the game's own milliseconds from the start date of the game. At calendar speed 1.00x a day is 4000 of them.

- **The count starts at the start date** (**Observed** on the 120 catalog saves, 568 to 604). The [day table](#the-day-table) begins at tick 0 on the start date in every one of them: 1 January of the header's start year in most, 1 January 1960 in 6428935, 26 May 1926 and 26 February 1999 in two others. In three catalog saves the header's start year and the table's first day disagree (1905 against 1 January 1900, 1950 against 1900, 1900 against 1910). Which one the game goes by there is **Open**.
- In three saves of one game (604, start year 1900, saved paused on 6 February, 20 February and 18 March 2060), every timestamp of a past event fell on or before the save day, and the newest was 0.7 of a day into the last one. **Observed**.
- **The date shown advances by the calendar speed times the stored clock** (**Confirmed** on 604, one game, always paused when saved). Set to 4.00x and run from 18 March to 17 September 2060 (183 days shown), the newest timestamp in the file moved by 45.6 days on the 1.00x scale: shown divided by stored is 4.01. Set to 2.00x and run to 9 March 2061 (173 days shown), stored moved 86.6 days: 2.00. Set to 0.50x and run to 21 April 2061 (43 days shown), stored moved 86.6 days: 0.50 (0.497). A fourth check predicted a date: the stored clock and the 0.50x speed put a save 33.9 days before 21 April 2061, so on 18 March, and the game showed 18 March 2061 when that save was loaded. The 4000 per day itself did not change with the speed: the stored clock used the same unit at 4.00x, 2.00x and 0.50x, and the speed only scales the date shown. Counted in shown days, one day is 4000 divided by the speed in stored units (1000 at 4.00x, 2000 at 2.00x, 8000 at 0.50x), which is the same rule written the other way round. So a bare timestamp gives a date only together with the speeds the game ran at, which is what the [day table](#the-day-table) records. The clock's rate in real time is in the bullet on play speed below.
- On loading a save written at 2.00x, paused, on 9 March 2061, the game came up paused at 2.00x with the same date (**Observed**, two loads, the second at 0.50x). So the date, the calendar speed and the pause state are all restored.
- **Durations shown in windows follow the same rule** (**Observed** on 604, 0.50x only). A stored duration is in clock units, so it shows as that many divided by 4000 days, multiplied by the calendar speed. Loan durations ([company.md](company.md#loans)) and subsidy durations ([subsidies.md](subsidies.md#the-offer-itself)) fit it. Whether the shown value follows the speed at the time of looking was not tested. A difficulty setting that scaled time would give the same factor, and one save cannot tell the two apart (**Open**).
- **No Lua value holds the date or the speed** (**Observed**). No number in the script states held either, and none changed from 1 to 4 between the 1.00x and 4.00x saves. The one `lastYear` number tracks the year in another script's state (see [notifications.md](notifications.md#the-availability-state)). The clock itself is `t1` in [the calendar speed field](#the-calendar-speed-field): in catalog save 6425796 the newest time in every `items*` list (199,285 lists) was exactly that `t1`.
- **Why 4000.** The game ships Teal type definitions of its Lua API under `api/tealdef/` in the install directory (read from the 604 build, **Observed**). In `api/engine.d.tl` the `GameSpeed` record, listed as `ComponentType.GAME_SPEED` next to `GAME_TIME`, holds `speedup` (the simulation multiplier, 0 when paused) and `millisPerDay`, described as the length of an in-game calendar day in milliseconds. `api/cmd.d.tl` has `makeGameSetCalendarSpeedCmd(millisPerDay)`, documented as changing only the calendar speed and not the simulation speed, which is what the calendar slider sends. `api/util.d.tl` has `getDefaultDayDuration()` ("default game ticks per day") and month and year durations computed from the current millisPerDay, and `api/engine/util.d.tl` has `getCalendarDate(gameTime)`, which returns the date "assuming current ingame speed". So the stored clock counts the game's own milliseconds, a day is 4000 of them at 1.00x, and the slider sets millisPerDay to 1000, 2000 or 8000 instead. The date shown is the stored clock divided by the current value, which is the rule measured above. The real-time rate was timed only at play speed 4 (next bullet: 1000 units per real second times the play speed); at 1x that rule fits a vehicle's age ([finances.md](finances.md#loan-payments-and-income-over-ten-minutes)), a subsidy countdown ([subsidies.md](subsidies.md#a-new-game-an-offer-its-expiry-and-an-accepted-subsidy-604)) and a ship's speed ([vehicles.md](vehicles.md#vehicle-instances-604)). The earlier games had the same idea as a per-install setting: `game.config.millisPerDay` in `res/config/base_config.lua`, default 2000, 1000 to 8000 listed as experimental, overridable by mods and not per map, see the [GOG forum thread](https://gog.com/forum/transport_fever/too_slow) and the [Transport Fever wiki's base config page](https://www.transportfever.com/wiki/doku.php?id=modding%3Adeveloperinfo%3Abaseconfig) (both about the first game; for the second game only workshop mods that change it were found).

- **The clock runs at 1000 units per real second times the play speed, whatever the calendar speed** (**Observed** on 604, one game, calendar stopped at `millisPerDay` 0, play speed 4 in three autosaves). The three autosaves came 300.7 s apart by file time and their clocks were 6,645,400, 7,845,400 and 9,046,200: 1,200,000 and 1,200,800 units, or 3,986 and 3,989 units per real second, which is 4 times 1000 within the save time. The first autosave came 216,800 units after the paused save it followed, which is 54 s of running at 4x inside a 300.7 s gap. A game with the date stopped therefore still advances the clock, and so does everything timed by it (bookings, production, vehicle movement).
- **The autosave interval counts real time, not clock** (**Observed**, same three autosaves, interval 5 minutes in the game's settings). The gaps between files were 300.73 and 300.76 s while the clock moved 1,200,000 and 1,200,800 units; an interval counted in clock units would have fired every 300,000 at 4x. The first autosave also fired 300.7 s after a manual save made with the game paused, with only 54 s of the gap spent running, so time spent paused counts, and the timer fits starting again at each save. A later autosave settles it: the game sat paused after the manual save `1401` (clock 10,026,200), and the autosave 301 s later (file times 14:01:23 and 14:06:24) was written at the same clock, 10,026,200, with play speed 0. So an autosave is written on schedule even when the clock is not moving, and the interval is wall time. The extra 0.7 s is about the time to write the file. Earlier saves of another test gave much longer and uneven gaps (a 15-minute setting, 54 and 16 minutes apart), so this holds for an unattended game at a steady speed only.

## The date in the header

The fifth u32 of the header, after the map width and height ([header.md](header.md)), is the date shown in the game, as a Julian day number, in the numbering of the [day table](#the-day-table).

- **Observed** on the 120 catalog saves (568 to 604): it equalled the day of the day table's last entry in all of them.
- **Confirmed** against the game's screen on three 604 saves: 2,451,652 in 6417707 (17 April 2000), 2,428,583 in 6425796 (18 February 1937) and 2,521,351 in 6428935 (14 February 2191).
- Values seen ran from 2,415,021 (1 January 1900) to 2,835,101 (21 February 3050, a game started in 2020). Saves of one game written on the same day hold the same value.

## The calendar speed field

Checked on 568 to 604. **Confirmed** on 604 for 0.50x, 2.00x, 4.00x and Paused (one game, saved five times, below); **Observed** on the rest.

It is a bare u32 in a small component. Nothing names it, so find it by the bytes around it (`01 00 00 00` is a u32 equal to 1):

```
09 00 00 00 00 00 00 00 | 01 00 00 00 | u32 millisPerDay | u32 playSpeed | 00 x 8
| 01 00 00 00 | 08 00 00 00 00 00 00 00 | 01 00 00 00 | u64 t1 | 01 | u64 t2
```

A u32 whose meaning is unknown sits just before the first `09` (3171 in one game, 53 in another). The whole pattern matched exactly once in every one of the 120 catalog saves and in six of our own, on every format version from 568 to 604. [tools/calendar_speed.py](../tools/calendar_speed.py) reads it.

- **`millisPerDay`** is the calendar speed, the field from the game's API files (see "Why 4000"). Four saves of catalog save 6425796's game (604, same date, paused each time, nothing else changed between them) differed from each other in this u32 and in the id lists the game writes in a different order each time, so a byte diff of the streams has to filter the second kind. Saved at 0.50x, 2.00x and 4.00x it held 8000, 2000 and 1000; saved on the Paused setting it held 0, and so did the earlier save of that game, which also read Paused. 1.00x is 4000 (catalog save 6417707, whose window read 1.00x, and 4000 is the commonest value in the catalog). Catalog save 6428935 holds 8000, matching its 0.50x.
- **Values seen in the catalog:** 0, 1000, 4000, 8000, 16000 and one 1,440,000, counted in [versions.md](versions.md#calendar-speed-in-the-catalog-2026-10-09). 2000 was not among them. 16000 would be 0.25x by the same rule, but no window was read for it, so that mapping is **Observed** only. The 1,440,000 save (mod 6430273) is not a slider step; why is **Open**.
- **It is the setting at save time, not a history.** Players mostly leave the speed alone but some change it over time (user report, not measured). Reasons given: to stay in a year whose vehicles they like, since availability and other date-based unlocks follow the date, and to hold back costs that rise in later years. Neither reason was checked here. The game's scripts do raise construction costs with the date, in 20-year steps ([inflation.md](inflation.md#the-year-cost-table)); an in-game test of it is still **Open**. The field alone cannot say how long a game ran at which speed; the [day table](#the-day-table) can. Catalog save 6428935 shows the effect: its shown date and its clock at plain 1.00x disagree by a factor of 0.88 although its field holds a single value (see [below](#calendar-speed-in-the-games-windows)). 70 of the 120 catalog saves hold 4000, but only 50 have a day table at 4000 ticks a day from start to end ([versions.md](versions.md#calendar-speed-in-the-catalog-2026-10-09)), so the setting is changed often enough to matter and a save at 4000 may have been run at other speeds earlier. **Observed**.
- **Paused (0).** The date stops and stays on the same day while the clock goes on counting (**Observed** in the game, one game: at the Paused setting the date shown stays where it was, and costs are tracked on the clock, not the date). The game's manual says calendar speed only changes when vehicles and infrastructure become available, and that cargo produced and consumed and vehicle maintenance are adapted to stay consistent ([Simulation overview](https://wiki.transportfever3.com/doku.php?id=gamemanual:simulation:overview), game manual), which fits. Whether the reporting window then shows the same period over and over was not checked in the stream. **Open**. The Paused setting and a paused game are separate: the same field holds 0 in saves that were running at 4x (catalog save 6422263, **Observed**).
- **Starting the calendar again after a long stop (604, Observed, one game, saves `1704` and `1705`).** With the date stopped for 17.2 million ticks the day table had one entry (1 January 1900, began at tick 0, in every save from `1703` to `1704`). After the player set 0.25x and let it run for a moment, the next save (`1705`, paused, `millisPerDay` 16000, clock 17,270,200) had two entries: 2 January 1900 began at tick 17,264,000, 6,200 ticks before the clock. A day at 0.25x is 16,000 ticks, so the calendar was set running at about tick 17,248,000, between the two saves. The header date was Julian day 2,415,022, the day table's last day and the date the player read on screen. So a game that was never run on the calendar keeps its first day for as long as the date is stopped, and the table grows from the tick the calendar starts. At `1706` (paused, clock 17,719,800) the table had 30 entries, the last 30 January 1900 beginning at tick 17,712,000 (7,800 ticks before the clock), and the screen showed Jan 30, 1900: 28 days after 2 January in 449,600 ticks, 16,000 per day at 0.25x. At `1708` (clock 18,891,800) the table had 103 entries, 13 April 1900 beginning at tick 18,880,000; 1707's 9 February began at 17,872,000, so 63 days took exactly 1,008,000 ticks.
- **A speed change made while running shows only as a change of day length (604, Observed, one game, five autosaves after save `1711`).** The player took the calendar from 0.25x to 0.50x with the game running at play speed 4 and did not say when. The autosaves held `millisPerDay` 16000 at 22,943,000 (22 December 1900) and 8000 at 24,143,000 (8 May 1901). The day table of the later one had every gap at 16,000 up to 4 January 1901, which began at tick 23,136,000, and every gap at 8,000 from 5 January on, at 23,152,000; no other gap length occurred. The change therefore falls in 4 January's 16,000 ticks, because the length of a day is fixed when the day starts (see the next paragraph for the test). At the clock's rate of about 4,000 units per real second at play speed 4 (see above) that is 48 to 52 seconds after the first autosave's file time, and the clock reached 24,928,000, the start of 15 August 1901 in the table, about where the file time of a screenshot taken on that date put it. The game keeps no list of speed settings: the table's gaps are the history, found in the calendar speed field and the day table only (the rest of the stream was not searched for another copy). The table is one entry per day, so a change cannot be placed inside a day, and two changes inside one day might leave no trace (not tested). The statistics periods are no help: they stay on 1,461,000 clock units whatever the speed, see [statistics-lists.md](statistics-lists.md), so only their date labels move with the table. **A change does not cut the day under way** (604, Observed, one game, saves `1712` to `1713` and the autosave after them). Saves `1712` (0.50x) and `1713` (1.00x) were made paused 21 seconds apart at the same clock, 26,751,000, 7,000 ticks into 30 March 1902; the only byte that differed in the speed field was `millisPerDay`, 8000 to 4000, and the day table, `t1`, `t2` and the header were identical. After the game ran on at 1.00x, the autosave's table shows 30 March, begun at tick 26,744,000, with its full 8,000 ticks, then every later day at 4,000 from 31 March at tick 26,752,000. So a new speed applies from the next day boundary, and the day under way keeps the length it started with, even when the change comes 7,000 ticks in; the table cannot place a change more finely than that day. The same held for a change to a longer day. The player went back from 1.00x to 0.25x and named 29 May 1903 as the date beforehand; the table of the autosave after it has 28 May 1903 at 4,000 ticks (begun at tick 28,444,000) and 29 May at 16,000 (begun at 28,448,000), and every later day at 16,000. Across the whole game the table holds four runs of day length, 16,000, 8,000, 4,000 and 16,000, matching the player's three changes (the first, to 0.50x, was dated from the table alone).
- **`playSpeed`** is 0 in every save written with the game paused (all of ours) and nonzero in running ones. Values seen: 0, 1, 2, 3, 4 and 8. Catalog save 6428935, whose author left it running at 2x, holds 2. It is probably the `speedup` of the API's `GameSpeed` record, whose order in the record is not the order here. **Observed**, not changed in the game.
- **`t1`** was 94,328,800 in all five saves of the 6425796 game, the newest timestamp of that game, so it is probably the game clock itself. Only one game was compared. **Observed**. **`t2`** equals `t1` in a paused save and trails it by exactly 200 times `playSpeed` in all 120 catalog saves (0, 200, 400, 600, 800, 1600). What `t2` is, is **Open**.
- **The speed steps.** The game's manual describes the calendar controls but lists no steps. The saves show 0 (Paused), 16000, 8000, 4000, 2000 and 1000, that is Paused, 0.25x, 0.5x, 1.00x, 2.00x and 4.00x. Transport Fever 2 offered full, half and quarter speed and a stopped date, per posts on its Steam forum; the third game keeps the idea and adds the faster steps.
- The date shown is the last day of the day table that follows this field, and the header holds a copy (see [the date in the header](#the-date-in-the-header)).

## The day table

Checked on 568 to 604. **Confirmed** on 604 against the date shown, one game saved five times and a second game; **Observed** on the 120 catalog saves.

Right after `t2` in the calendar speed field comes the table that turns a clock value into a date, which the history charts need:

```
u32 n
n x ( u64 tick, u32 day )
```

`day` is a Julian day number (2,415,021 is 1 January 1900; Python: `date.fromordinal(day - 1721425)`), and `tick` is the clock value at which that day started. [tools/calendar_speed.py](../tools/calendar_speed.py) reads it.

- **The date shown is the last entry's day.** In catalog save 6425796 (start 1900) the table had 13,563 entries, one per day, with consecutive day numbers from 2,415,021 to 2,428,583, which is 18 February 1937 as the game showed it. In a later save of our own of catalog save 6417707's game, paused on 17 September 2000 at 1.00x, it held 36,785 entries ending on that date, with every entry exactly 4000 ticks after the one before, so tick 134,408,000 is 1 January 1992.
- **The date of any tick is the last entry at or before it.** That is how the stored clock, the speed history and the date fit together without a division: the gaps between entries are the length of each day in ticks at the speed then in force. In 6425796 the day lengths were 1000 for 6,952 days (4.00x), 4000 for 5,188, 2000 for 897, 16000 for 316 and 8000 for 199, plus a handful of other gaps. A bare timestamp gives no date at speeds other than 1.00x, but a timestamp and this table do.
- **A stopped calendar makes one long day.** No entries are added while `millisPerDay` is 0, so the clock keeps counting and the current day gets longer. In 6425796 the last entry began at tick 76,984,000 and `t1` was 94,328,800, so 17,344,800 ticks had passed on 18 February 1937 (4,336 days at 1.00x), which fits the date staying put at the Paused setting. The few large gaps inside the table (5,812,000 and 7,032,000 for example) are probably earlier stops, but that was not checked. **Observed**.
- **`t1` lies inside the last day.** In all 120 catalog saves `t1` minus the last tick was less than `millisPerDay`, or `millisPerDay` was 0, and the first entry was at tick 0. **Observed**.
- **The table is not always one entry per day.** In 32 of the 120 catalog saves (counted in [versions.md](versions.md#calendar-speed-in-the-catalog-2026-10-09)) the day numbers are not consecutive or the ticks are not rising. Seen: a jump forward of years between two entries (a game starting in 1900 whose table jumps to 2026 after ten days), a jump back to 1900 followed by another jump at the same tick, and long runs of the same day number with the tick going up by 4000 each. The manual says the date can be set in sandbox mode, so jumps are probably date edits, but no edit was made here. **Open**. A reader that wants the date should take the last entry (or the header's copy) and not assume every entry is the day after the last.
- Start dates other than 1 January are possible: two catalog saves begin on 26 May 1926 and 26 February 1999 (**Observed**).
- **The charts bin by clock period, not by this table.** The yearly bars of [statistics-lists.md](statistics-lists.md#the-yearly-bars-are-periods-of-1461000-units-604) are periods of 1,461,000 clock units. The entry at tick 134,411,600 sits in 1992 by this table (1 January 1992 started at 134,408,000 in that game) but before the period boundary 92 x 1,461,000 = 134,412,000, and the window counted it in 1991. The table gives only the date label under each bar. **Observed**, 604.

## Calendar speed in the game's windows

- **Not a Lua key or a game setting.** The calendar speed (the 1.00x slider of the Weather and Time window) is not a key in any script state, and not in the game's `settings.lua` either (604; the file holds graphics, audio, unit and camera settings plus the remembered new-game choices). It is the `millisPerDay` of the `GAME_SPEED` engine component. Components are written without their names: one 604 stream had no `GameSpeed`, `millisPerDay` or `speedup` strings at all.
- **The Paused setting in the window.** In catalog save 6425796 (604) the Calendar Speed row read **Paused**, with the slider at its left end, while the game was paused and showed 18 February 1937; saves of the game played into 2061 read 0.50x and so on in that row while paused. That is `millisPerDay` 0, a setting of its own ([above](#the-calendar-speed-field)). The newest stored timestamp there was 94,328,800 (26 July 1964 at plain 1.00x) against 54,248,000 for the date shown at plain 1.00x, a ratio of 0.575, which the [day table](#the-day-table) explains: mixed speeds and a long stop. **Observed**.
- **Restored from another player's save.** Catalog save 6428935 (604) showed 0.50x in the Weather and Time window after loading, and the game came up running at its 2x play speed (the author saved it unpaused). A copy re-saved paused from that game, reloaded, came up paused and showed 0.50x again (**Observed**, one round trip). The loan offers fit the same speed, see [company.md](company.md#loans). Its shown date, 14 February 2191 from a 1960 start, is 84,416 days from 1 January 1960, while the newest stored timestamp is 95,878 days at plain 1.00x. The ratio is 0.88, which fits a game played at several speeds and so says nothing about the speed at save time.
