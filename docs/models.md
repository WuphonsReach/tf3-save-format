# Models: the model table and model instances

Two structures tie things on the map to 3D models: a table of every model the save can use, and a model instance record for each placed thing that has one. The animals ([animals.md](animals.md)) and the hot air balloon ([fun-elements.md](fun-elements.md#the-model-instance)) use them. The fields match the `ModelInstanceList` component and `ModelInstance` record in `api/tealdef` (a model id, the transform at the previous frame, the transform). **Observed** on 604 in eighteen test saves (the animal test series of [terrain.md](terrain.md#what-was-compared) and others).

## The model table

The first thing after the header ([header.md](header.md)): a `u32` count, then per model

```
str  source mod (empty for the base game)
str  path
u32  id
```

- The ids run 0, 1, 2 and so on in table order. They are the index into the table, and they depend on the models installed, so read them from the save and do not carry them from one save to another.
- The base game's 4,473 models come first, sorted by path, so the 28 models under `animal/` are ids 0 to 27. A mod's models follow, one run per mod in the order of the mod list, and carry the mod's id (a save with seven mods, [mods.md](mods.md#seven-mods-in-one-new-game), had 4,473 base models and 64 from six mods, and one of the seven added none): `urbangames_deluxe_upgrade_pack` adds 31, among them `animal/bison/bison.mdl`, `animal/boar_m/boar_m.mdl` and `vehicle/zeppelin/hot_air_balloon/hot_air_balloon.mdl`.
- An earlier reading as `u64 id, str path` fits the base game's models only because their source string is empty: the previous entry's id and the next entry's empty string make eight bytes. The three-field layout is the right one.

## The model instance record

Somewhere after the header (2.7 to 3.9 MB in the animal test saves) there is one record per placed thing that has a model: a `u32` count of instances, then the instances.

- An instance is 137 bytes. It starts with the `u32` model id, then two 4 x 4 `f32` matrices one byte apart, with the translation in floats 12 to 14. In the instances read, both matrices held the same translation. The other bytes of an instance are **Open**.
- In the animal records the count is one for the animal plus one per flock offset, and 9 bytes separate one record's last instance from the next count (146 bytes for an animal without a flock). The first instance's translation equals the animal's `worldPosition`.
- **Find a record** by searching for the 12 bytes of a known position (as `f32` x, y, z) and reading the model id as the `u32` 52 bytes before it. The balloon's record was found this way.
- The records of the animals are in the order of the animal list. A record for a thing that has left the map is gone: no instance used the balloon's model after it had flown off.

## Vehicles, people and animals in one run

**Observed** on 604, one game (the Small subarctic game of [finances.md](finances.md#a-first-build-out-row-by-row), two saves, 4 ships and 3 horse carts on the map). Vehicles do keep a model instance of the 146-byte kind above, one per vehicle, with its translation in floats 12 to 14. In the later save the run held 572 consecutive instances (stride 146, no gaps) and mixed animals, vehicles and people: an orca, the three horse carts (model `vehicle/road/truck/horsewagon_1850_v2`), the four ships (`vehicle/ship/british_columbia`), then runs of people (`characters/`) and coaches.

- **Find a vehicle** by its model: look up the model's id in the model table (the ships' id was 4192), then scan the stream for that `u32` followed by a 4 x 4 `f32` matrix whose floats 3, 7 and 11 are 0 and float 15 is 1. The four ships gave exactly four hits, 146 bytes apart.
- **Ships keep their order, and the order is the vehicle number.** Before sailing (a save with all four in the depot) the four instances held one identical position and heading, the ship depot's spawn point; later each had its own, so the slot order is stable. Slot 4 is Ship 4: the player described Ship 4 as loaded (10/10) and waiting outside the dock area for Ship 2 to finish unloading and leave, Ship 2 as at the dock and Ships 1 and 3 as empty and heading out, and the saved positions and headings agree (below). The journal agrees as well: the vehicle running-cost bookings come in the same order ([finances.md](finances.md#running-costs-upkeep-loan-payments-and-income-over-ten-minutes)), and the fourth one sums to Ship 4's own figure. The slot with the ship at the dock sat at 410.8 and 4,986.7, 120 to 370 m from the carts at the nearby stop. **Observed**, one game with four ships.
- **Coordinates.** Values ran from -1,548 to 1,427 in x and -4,926 to 5,450 in y over the whole run, with ships at z = 0 (water level) and land things at 3 to 8. The map is 4,608 x 13,824 m, so the origin is probably the map's centre, not a corner. **Open** (no object near an edge was seen).
- The matrix's top-left 2 x 2 holds the heading as a rotation about the vertical axis, and the first row (floats 0 and 1) is the direction the ship faces. In the save the four ships read: slot 1, (1, 0) at x 1,108, y 4,152, the farthest from the port, facing east, away from it; slot 2, (0.27, 0.96) at the dock; slot 3, (0.14, -0.99) 380 m south of the dock, facing south, away from it; slot 4, (-0.99, 0.14) at x 613, y 4,950, about 200 m from the dock, facing west towards it. That is outbound, at the dock, outbound and queued for the dock, as the player saw. A ship waiting for a free berth is therefore still stored at a position, facing its stop. **Observed**, one save. Slot 1 held the identity rotation exactly, which may only mean it faced due east.
- **A second save, 62.4 s later** (clock 632,200 against 569,800, paused again): the four ships read, with the player's description of each: slot 1 at x 1,326, y 4,147, "sitting at the fishing grounds" (218 m east of where it was); slot 2 at 390.4, 4,910.9 facing (-0.39, -0.92), "leaving the port" (78 m south-west of the dock); slot 3 at 703, 4,158 facing (0.99, -0.12), "heading out to the fishing area" (east, towards slot 1); slot 4 at 470.9, 4,972.5 facing (-0.98, 0.22), "heading into the port, not far out now" (61 m east of the dock, facing it). All four headings agree with what the player saw, so the first row of the matrix is the facing direction. The ships' windows in that save read 26 km/h for Ship 4 and 35 km/h for Ship 3. Ship 3 had moved at least 563 m in the 62.4 s since the earlier save (the straight line between its two positions), 9.0 m/s or 32.5 km/h, so a speed of 35 km/h fits clock units being milliseconds. Ship 4's 143 m in the same time is 8.3 km/h on average, which is lower than its 26 km/h because it waited for the dock for part of it (that it equals the 8 km/h its window showed a save earlier is chance). One pair of ships, so a rough check. The previous-frame matrix again equalled the current one. **Observed**, one game.
- **A vehicle in a depot has no instance.** A later save (six ships) held five ship instances: the four trawlers (`british_columbia`) and one `sydfart` at sea, 1,266 and 4,581. The sixth ship, a `dunara_castle` standing in a ship depot ("In Depot" in its window), had none. So that vehicle, in a depot, had no instance, but not every vehicle in a depot lacks one: see the next bullet. The player's reading is that a ship in a depot that is **not assigned to a line** has no instance, which fits both observations (the `dunara_castle` had no line; the ships of the next bullet had one). **Observed**, one ship.
- **Ships bought and not yet sent do have instances, all at one point.** In the Series A save `1312` (made right after two new ship lines were set up, none of the new ships sailing yet, according to the player) the journal had 13 new ship purchases, and the stream had 13 new ship instances: 8 of `british_columbia` (the model of the 256,032 purchases) and 5 of `sydfart` (the 438,912 ones, the model of the old Ship 6). All 8 of the first model read one position (x 861.1, y 4,761.4, z 0) and one heading (0.99, -0.16), all 5 of the second another (869.4, 4,760.1) with the same heading, 8 m apart, and the four old ships and the old Ship 6 stayed where they were in the save before. So a depot's spawn point is stored as the position of every vehicle waiting there, as in the first test above. These ships had been put on a line (TOD Fishery 2 and 3, see [lines.md](lines.md#a-new-line-and-its-vehicles)); the `dunara_castle` that had no instance had not. The player's reading is that it is the line assignment that gives a waiting vehicle an instance. The tests so far do not settle it. After the player took Ship 8 (of Ships 7 to 11, line TOD Fishery 2) and Ship 18 (of Ships 12 to 19, TOD Fishery 3) off their lines, as the line lists in the screenshots show, the saves `1322` and `1323` (paused at clock 5,997,000) held all 18 ship instances (12 `british_columbia`, 6 `sydfart`) with the ship records byte for byte the same as in `1312`; `1324` (clock 6,003,400) and `1327` (6,084,200) still held 12 and 6, with ships leaving the depot one at a time. In `1327` one `sydfart` was still on the spawn point and was taken to be the unassigned Ship 8, but in `1328` (clock 6,215,400) all five new `sydfart` ships were sailing east, so that one was waiting for its turn and not Ship 8. The player's line windows after the run show why: Ship 8 and Ship 18 were back on TOD Fishery 2 and 3 (Ships 7 to 11 and 12 to 19 again), without the player putting them back. So taking a ship off its line while the game is paused and it is in the depot did not last once the simulation ran, and the ship left with the others. In `1328` three of the eight `british_columbia` (Ships 12 to 19) had left, as the player counted, and five were still on the spawn point, which is the four assigned ships still waiting and the unassigned Ship 18 if it kept its instance; the save cannot tell which is which, since an unassigned ship and a waiting one look the same (same position, same heading). The test of the idea therefore needs a ship that stays unassigned while the game runs (a new ship bought and not given a line). Why the `dunara_castle` had none is **Open**. Where a ship's line is stored was not found: any two paused saves of this game differ by tens of thousands of bytes in the statistics area (even `1322` against `1323`), so a byte diff does not isolate the change.
- **A second test: a ship sent to a depot with no line.** Ship 18 was ticked alone and sent to a depot with "Send Selected Vehicle to Depot" (its line colour went and a depot icon showed in the list), and it appeared in the depot list of the ship depot "East", beside Ship 5, the `dunara_castle` that has no line either. Saves `1333` (clock 6,242,200), `1334` (6,287,000) and `1335` (6,304,600) each held 12 `british_columbia` instances, which is the four old ships and all eight new ones, Ship 18 among them, so a ship in a depot with no line did not lose its instance. In `1335` exactly one of the 12 had not moved since `1334` (17,600 units earlier): at (861.6, 4,761.3), 0.5 m from the first depot's spawn point, heading (0.99, -0.16); all the others, including the `sydfart` ships, had moved. That stationary instance is the best candidate for Ship 18 (the same slot was one of the four on the spawn point in `1333`, the others of which left), but the save does not name it, so it rests on elimination. The `dunara_castle` still had no instance in `1335`. The player recalls that Ship 5 was a large ship bought for the first fishing line, found too big for the small pier and sent to the depot afterwards, so it got there the way Ship 18 did. The next save, `1339` (clock 6,428,600), held 11 `british_columbia` instances, not 12, and the stationary one at (861.6, 4,761.3) was gone: Ship 18's instance was dropped some time after the ship was parked. The running-cost bookings put Ship 18 in the depot at about 6,280,000 ([finances.md](finances.md#a-ship-parked-in-a-depot-pays-5-of-its-running-costs-604)), so it still had its instance 24,600 units later (`1335`, 6,304,600) and no longer 148,600 units later; where in between it went is not known (no save between). So the player's idea holds, with a delay: a ship that is parked in a depot with no line ends up with no instance, as Ship 5 has none. The earlier unassigned test was not valid (Ships 8 and 18 were back on their lines when the game ran, see above), and this one is the clean case. A ship waiting at a depot on a line keeps its instance at the spawn point. **Observed**, one ship against another, identification of Ship 18 by elimination.
- **The slot order is not the vehicle number once vehicles have been added.** The first four `british_columbia` ships sit in the 146-byte block as before, but the 8 new ones and the new `sydfart` ships are scattered through the instance data, 3,000 to 97,000 bytes apart, with the old Ship 6 in the middle of the `sydfart` ones (after three new ships and before two). So the instances are in slot order, and new ones take free slots as entity names do ([entity-names.md](entity-names.md#what-a-rename-and-new-building-do-to-the-table-604)); which new ship is which number was not worked out. **Observed**, one save.
- The second (previous-frame) matrix held the same translation and rotation as the first in all four ships, so the save, made with the game paused, gives no speed or direction of travel apart from the heading. The other bytes of the four instances (the flag byte between the matrices and the 13 bytes after them) were identical, so no velocity is in the record either. A search for 8 km/h as an `f32` or `f64` in m/s (2.22) found nothing in the stream, but the window rounds, so that proves little. **Observed**, one save; where a ship's speed is kept is **Open**.
- The 9 bytes between records and the other bytes of an instance are still **Open**.

This settles the question left in [entity-names.md](entity-names.md#not-found): a vehicle's position and model are in this run, though still not next to its entity id.
