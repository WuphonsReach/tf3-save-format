# Models: the model table and model instances

Two structures tie things on the map to 3D models: a table of every model the save can use, and a model instance record for each placed thing that has one. The animals ([animals.md](animals.md)) and the hot air balloon ([fun-elements.md](fun-elements.md#the-model-instance)) use them. The fields match the `ModelInstanceList` component and `ModelInstance` record in `api/tealdef` (a model id, the transform at the previous frame, the transform). **Observed** on 604 in eighteen test saves (the animal test series of [terrain.md](terrain.md#what-was-compared) and others).

## In short

All 604; the layouts were read in eighteen test saves and two catalog saves.

- **The model table follows the header: a `u32` count, then per model `str` source mod (empty for the base game), `str` path, `u32` id (Observed).** Ids rise in table order but skip, depend on the installed models and must be read from the save. An instance carries the stored id, not the index (Observed, a 10,252-entry table).
- **A placed thing with a model has a 137-byte instance record: the `u32` model id, then two 4 x 4 `f32` matrices one byte apart, translation in floats 12 to 14 (Observed).** Records sit in one run with 9 bytes between them (stride 146). The run mixes animals, vehicles, people and cars. Find a record by a known position, with the model id 52 bytes before it.
- **The first matrix row is the facing, and its length is the scale (Observed).** A train is one instance per unit, not one record per train.
- **Trees, rocks and a farm's fences and props are instances too (Observed, one editor map);** a deleted instance stays in the table for one save and its slot is reused. Brush-painted trees are a different 24-byte record in per-cell runs.
- **Land industries declare a `ground_face` polygon in their script that the Towns layer paints; water industries declare none (Observed, one editor game; 4 of 29 compared with screenshots).**
- **Open:** why ids skip, the other bytes of an instance, how a generated map's forests are stored, and the list after the last run of brush-painted trees (a `u32` count of 7,073 in one save).

## The model table

The first thing after the header ([header.md](header.md)): a `u32` count, then per model

```
str  source mod (empty for the base game)
str  path
u32  id
```

- The ids start at 0 and rise along the table in table order, and they depend on the models installed, so read them from the save and do not carry them from one save to another. They are not always the index into the table: catalog save 6417707 (604, no mods) has 4,473 entries and ids up to 4,486, with 14 missing in six places, and catalog save 6409998 (604, dozens of mods) has 10,252 entries and ids up to 12,190, with 20 skipped where the first mod's models begin and more later. Why ids skip is **Open**. A model instance carries the stored id, not the index (**Observed**, 6409998: read by id, its bus and truck instances come to 285, the road vehicle count in its header ([header.md](header.md#counts-the-load-dialog-shows)); read by index they come to 207). `read_model_table` in [model_instances.py](../tools/model_instances.py) keeps the ids and `read_instances` maps by them.
- The base game's 4,473 models come first, sorted by path, so the 28 models under `animal/` are ids 0 to 27. A mod's models follow, one run per mod in the order of the mod list, and carry the mod's id (a save with seven mods, [mods.md](mods.md#seven-mods-in-one-new-game), had 4,473 base models and 64 from six mods, and one of the seven added none): `urbangames_deluxe_upgrade_pack` adds 31, among them `animal/bison/bison.mdl`, `animal/boar_m/boar_m.mdl` and `vehicle/zeppelin/hot_air_balloon/hot_air_balloon.mdl`.
- An earlier reading as `u64 id, str path` fits the base game's models only because their source string is empty: the previous entry's id and the next entry's empty string make eight bytes. The three-field layout is the right one.

## The model instance record

Somewhere after the header (2.7 to 3.9 MB in the animal test saves) there is one record per placed thing that has a model: a `u32` count of instances, then the instances.

- An instance is 137 bytes. It starts with the `u32` model id, then two 4 x 4 `f32` matrices one byte apart, with the translation in floats 12 to 14. In the instances read, both matrices held the same translation. The other bytes of an instance are **Open**.
- In the animal records the count is one for the animal plus one per flock offset, and 9 bytes separate one record's last instance from the next count (146 bytes for an animal without a flock). The first instance's translation equals the animal's `worldPosition`.
- **Find a record** by searching for the 12 bytes of a known position (as `f32` x, y, z) and reading the model id as the `u32` 52 bytes before it. The balloon's record was found this way.
- The records of the animals are in the order of the animal list. A record for a thing that has left the map is gone: no instance used the balloon's model after it had flown off.

## Vehicles, people and animals in one run

**Observed** on 604, one game (the [Small subarctic game](test-games.md#small-subarctic-game), two saves, 4 ships and 3 horse carts on the map). Vehicles do keep a model instance like the animals' above (137 bytes, 146 apart with the 9 bytes between records), one per vehicle, with its translation in floats 12 to 14. In the later save the run held 572 consecutive instances (stride 146, no gaps) and mixed animals, vehicles and people: an orca, the three horse carts (model `vehicle/road/truck/horsewagon_1850_v2`), the four ships (`vehicle/ship/british_columbia`), then runs of people (`characters/`) and private cars (`car` models `coach_01` to `coach_03`, horse coaches).

- **A train is one instance per unit (Observed, 604, one train).** In an autosave of catalog game 6425796 a stopped passenger train (the `class_prr_gg1` unit at the front and 8 `streamlined_nyc` cars, the 8 the player's window showed) was nine instances in nine places of the run, not next to one another in it. The cars lay 24.8 to 25.6 m apart along the track behind the `class_prr_gg1`, all facing the way it did (-y, first transform row about -0.1, -1), so the facing is the direction of travel and the unit's length is not in the instance. [terrain_map.py](../tools/terrain_map.py) `--vehicles` draws each unit as a five-sided shape (a rectangle with a pointed front end).

How to find a vehicle's instance, and what a depot, a line, a purchase or a sale does to it, is in [vehicles.md](vehicles.md).

## Industry footprints: the ground face from the industry's script

**Observed** on 604, one game (the [Tiny flat editor game](test-games.md#tiny-flat-editor-game), save `1963`: a farm, a forest, a saw mill and a livestock farm, compared with five Towns-layer screenshots of the same game). The polygons are from `<key>/<key>.script.lua` in `base/content/industries/<key>.zip` (the key is the folder name in the industry's model paths, as [industry-chains.md](industry-chains.md) uses).

- **The Towns layer paints each industry purple: a dark outline round a light, translucent fill, with the buildings inside tinted darker.** The shape is a polygon, not a circle or the lot; the access street ends on one of its edges. The black outlines round farm fields beside an industry are a different shape and are not tinted.
- **Land industries declare that polygon: one `ground_face` curve of 4 to 93 points, in the industry's own axes.** Place it as the depot face in [depots.md](depots.md): the main model's origin and facing, local x along the facing. Twenty-nine industries of the base game declare one (the farms, forest, mines, quarry and pits, and every factory and works). Four checked: a farm 120 by 180 m, a livestock farm 150 by 120 m (x from -81.1 to 68.9), a forest 130 by 120 m with an 80 by 20 m notch cut from one corner, a saw mill a 13-point stepped shape about 218 by 102 m. Their outlines and notches, and the end of the access street on an edge, matched the screenshots, and the saw mill came out about 1.5 times the livestock farm's width in both. The other 25 were read, not compared with the game.
- **The water industries declare no polygon, yet the layer outlines two (604, Observed, one game, one or two pictures each).** Registered on the corner buoys, a **fishing ground's** outline is a strip about x -40 to 22, y -28 to -12 plus a body about x -40 to 38.5, y -13 to 20.7 with one corner cut, within 1.5 m of its terminal model boxes; a **sand excavator's** is one rectangle about x -18.2 to 45.5, y -43.5 to 65 m (within 2 m of its models). An **oil platform has no outline**, only tinted meshes and round parts: two docking stations at x ±55 m (the orange drums, about 10 m across) and four large buoys at (±20, ±70) (2 to 3 m); all 18 had the same. Its deck is about the `oil_platform_sm` box (x -24.5 to 24.7, y -29.5 to 24.7), with the helipad (an octagon about 21 m across) at a corner and the big crane's boom (4 m wide, to y of about 52) along +y, which show its facing. The pictures are tilted (deck-height parts sit about 13 m toward +x and 8 m toward -y of their plan place), so the boom's tip is good to about 3 m. **Open:** full or `_sm` boxes, a count that follows production, mods' industries.
- **`terrain_map.py` draws it** under the industry badge from the install at run time, nothing stored ([tools/README.md](../tools/README.md)). The model origin is not the polygon's centre (for the 29 the bounding-box centre is 0 to 56 m from it: 17 within 20 m, the chemical plant, iron ore mine and tire factory 45 to 56 m), so the badge sits on the polygon's centroid, and is 0.4 of its shorter side across.

## Evidence and tests

### Trees, rocks and farm fields are model instances

**Observed** on 604, one Tiny tropical editor map ([Tiny flat editor game](test-games.md#tiny-flat-editor-game), saves `1952` to `1959`). The instance table of that map held 28,700 to 32,000 instances: about 23,700 that stay put (town props such as hedges, fences, flowers and plants, trees, and the farm's fences, plants and animals standing at 0, 0), the rest people, vehicles and bird flocks, whose positions change from one save to the next, so a diff of two saves has to leave those out (`era_*`, `coach_*`, `bird_*`, `cougar` here).

- **A placed tree or rock is one instance.** The editor's exotic large tree (`brleaf_06`) at (0.0, -1035.5, 5.0), a cracked rock (`cr_rck_04`) set 50 units above the ground at (130.2, -1286.0, 55.0), and a fruit tree (`pc_tr_01`) at (104.7, -1285.2, 5.0) each added one instance, with z the ground height (5.0 on this flat map) plus the offset. In the record the matrix reads as rows: a 2 x 2 rotation about the vertical axis in the first two rows, a third row (0, 0, scale, 0) (read for the rock only) and the translation and a 1.0 in the last.
- **The scale is in the rotation rows (Observed).** Each of the first two rows has length equal to the scale, so the length of the `facing` pair `model_instances.py` prints is the scale and it is not a unit vector. The three placed things read 0.801, 0.800 and 0.802; the town's existing `pc_tr_01` trees read 0.475, 0.650, 0.772 and 1.0 and above, so the scale does vary.
- **A deleted instance stays in the table for one save, and its slot is reused (Observed, once).** The rock was in the table in the save made after its delete and went in the next, where the fruit tree took its slot number (30627). The same lag holds for road edges ([editor-saves.md](editor-saves-tests.md#a-delete-reaches-the-edge-table-with-the-next-new-road)).
- **A farm is about 1,450 instances.** Placing a small livestock farm added 1,451 that stay put (576 `lf_fence`, 102 `hay_cube`, 73 `ch_f_plm_01`, 67 `plmt_01`, 52 `pallet`, 50 `cow_prod_high` and more); the field that vanished when a road was drawn beside it ([editor-saves.md](editor-saves-tests.md#a-running-clock-a-tree-a-farm-and-a-rock)) probably took its fence with it: 199 instances left the table in the next save, 108 of them `lf_fence`, one save after its module record went.
- **The tree tool's settings land in the instance (Observed, 604, saves `1960` and `1961`).** The tool has Height, Rotation, Random Rotation and No Collision settings, and places one tree or a brush of them. No Collision only lets the player place a tree where the game would refuse it (the player's report); whether a tree placed that way is marked in its instance was not tested. Five old bushes with flowers (`eldrbr_01`) placed with Height 0.0, Rotation 80 degrees and Random Rotation off came out as five instances at z = 5.0 (the flat ground), all with the same facing pair, which reads as an angle of -80.2 degrees: the stored angle is the negative of the one on the slider (the pair is printed to two decimals). Five palms (`smpl_plm_01`) with Random Rotation on read 117.5, 148.3, 178.6, -150.9 and -120.1 degrees, steps of about 30.5 degrees one after the other, so the "random" angles were not independent draws. The new instances were consecutive slots (five in a run each time) and the stream grew by 45.5 KB for the bushes and shrank by 1.0 KB for the palms, with the clock running, so the size says little about one tree.
- **The scale is not on the sliders.** The bushes all read 0.995, the palms 0.798 to 0.801, and the earlier tree, rock and fruit tree 0.800 to 0.802, though no scale was set: it varies by model, and a little between copies of one model (palms) or not at all (bushes).
- **Brush-painted trees are a different record: 24 bytes each, in groups (Observed, 604, save `1962`).** A forest painted with the tree tool's brush (several mouse holds, 14 species ticked, random rotation on) added no instance of the 137-byte kind: `model_instances.py` listed none of its trees. The stream held 232 new 24-byte records instead: `u32` model id (an index into the model table, [above](#the-model-table)), `f32` x, y and z (5.0 on this flat map), `f32` angle in radians (-3.13 to 3.13) and `f32` scale (0.806 to 1.196). They come in runs, each run a `u32` count and then that many records, with five zero bytes between a run's last record and the next count: 20 runs of 20, 15, 13, 1, 1, 20, 54, 12, 3, 2, 45, 10, 7, 7, 1, 6, 8, 3, 1 and 3 records. A run is the records of one 32 m terrain cell (the next bullet), not one stroke as first guessed here. Every run lies in the same 60 by 80 m patch and mixes species (13 of them: `hdg_01`, `bn_plt_01`, `crl_plm_01`, `eldrbr_01`, `ch_f_plm_01`, `pc_tr_01`, `ccn_plm_01`, `smpl_plm_01`, `bsh_01`, `dt_plm_01`, `brleaf_07`, `plmt_01`, `brleaf_04`). The first run follows straight on from the tail of a 137-byte instance record. Find them by a chain of such records, not by an offset; the angle in radians and the scale between 0.8 and 1.2 pick them out. The stream grew by 14 KB, the records and their counts being 5.7 KB of it.
- **A run is one 32 m cell, and a click is one lattice (Observed, 604, saves `1962` and `1963`).** A single click of the tree brush set to the solid circle (size 75.5, strength 100%, Random Rotation on, the same 14 species ticked) added 93 records in 9 runs of 8, 6, 1, 1, 13, 18, 8, 21 and 17, straight after the last run of `1962`. Each run held the records of one 32 m by 32 m cell of the map (cell = floor of x and y over 32): the nine runs were nine different cells of a 3 by 3 block, where `1962`'s 20 runs fall in two passes of 11 and 9 cells (cells repeat between the passes), so a run is a cell's share of one drag or click and the cells come in no sorted order. The 93 trees of the click all sat on one 1 m lattice, x ending in .11 and y in .73 (the fractions are what the click picked), 93 different sites of the roughly 4,500 sites inside the circle, so about one site in 48 got a tree. The forest of `1962`, painted by dragging, has about a dozen lattices, one per mouse step, with different fractions. The click spread over 78 m in x and 72 m in y (wider than the 75.5 on the slider), with distances from its centre as for an even spread over a disc of about 39 m radius. Angle (-3.02 to 3.10 radians) and scale (0.801 to 1.196) were as in `1962`; z was 5.0; all 14 species came up (`brleaf_06`, absent from `1962`'s 232, among them). Stream: 16,569,025 bytes in `1962`, 16,582,081 in `1963` (+13,056 B, of which the records and counts are 2.3 KB); the first run moved 23,587 B later, so parts before and after the runs changed size too (not traced). The list after the last run (a `u32` count, 7,073 in `1962`, 8,582 in `1963`) grew by 1,509 for the click; what it holds is **Open**.
- **Generated maps do not hold chains of these (Observed, 604, one Tiny and one Large save).** A search for 50 or more 24-byte records in a row, any z, found none (z within the height range) in the Tiny tropical save at game start (15.7 MB stream) or the Large tropical autosave (184 MB). So the "hundreds of thousands of trees" guess is not met by this record in a generated map; how a generated map's forests are stored was not found (**Open**).
- **Not yet read:** which models are trees, which rocks and which props from the model names alone, and whether the large forests of a generated map are instances too (not counted).
